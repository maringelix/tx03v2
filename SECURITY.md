# Security policy

## Reporting a vulnerability

Report privately through GitHub: **Security > Report a vulnerability** on this repository (private
vulnerability reporting is enabled when the repository is public, see `docs/PUBLISHING.md`). Do not
open a public issue. Never include credentials, project IDs or numbers, billing accounts, service
account e-mails or IP addresses; use placeholders.

This is a personal educational project: reports are handled on a best-effort basis, with no response
time guarantee and no bug bounty.

## Supported versions

Only the latest commit on `main`. There are no releases yet.

## What this repository does to stay safe

The rules, where each one is enforced and the known limits are in
[docs/GUARDRAILS.md](docs/GUARDRAILS.md). In short:

- The harness (`make verify`, also the CI) runs gitleaks, trivy (HIGH/CRITICAL), tflint, actionlint,
  shellcheck, kubeconform and policy checks that block real identifiers, unpinned actions and the
  regressions found in v1.
- GitHub Actions reach Google Cloud only through Workload Identity Federation: the provider of the
  pool `tx03v2-github` accepts tokens of the two lab repositories only, by the numeric IDs of the
  owner and of the repositories (a deleted and re-registered account name does not inherit the lab),
  and each CI service account can be impersonated by one exact, immutable subject per grant
  (`repo:<owner>@<id>/<repository>@<id>:...`). There are no service account keys anywhere (the harness
  refuses `google_service_account_key` and `credentials_json`). The list of people who deploy from a
  laptop is a repository secret, masked element by element in the logs.
- The CI service accounts have roles only in the dedicated lab project. The apply identity may grant
  project roles only from a fixed list of four (an IAM condition on `modifiedGrantsByRole`);
  `roles/owner` is never granted and nothing is granted above the project.
- GKE Autopilot with private nodes and no public IP endpoint; people and CI reach the control plane
  through the DNS-based endpoint, where every request is authorized by Google IAM (Kubernetes tokens
  and certificates through that endpoint stay off) and then by Kubernetes RBAC.
- Cloud SQL has no public IP and no VPC peering: only a Private Service Connect endpoint, encrypted
  connections only and the shared regional CA, so the app can verify the server name (`verify-full`).
- External Secrets reads exactly the two lab secrets as the Kubernetes ServiceAccount of its
  controller (Workload Identity Federation for GKE); no Google service account or key exists for it.
- The database password and the admin token are generated by ephemeral resources and written with
  write-only arguments: they are never stored in the Terraform plan or state, and the plan identity
  never reads a secret value.
- Every harness tool is pinned by version and SHA256; actions by commit SHA; the External Secrets
  chart by OCI manifest digest and archive SHA256; images by digest.

## Known limits

v2 has never been applied to Google Cloud (`not run in the cloud (v2)`): the Terraform tests use a
mocked google provider. Inside the lab project the apply identity is still powerful: the admin role of
each service the lab uses (Kubernetes Engine, Cloud SQL, Compute networking and security policies,
DNS, Artifact Registry, Parameter Manager) and a Secret Manager role that creates and grants secrets
but cannot read a value. There is no Editor, no Secret Manager Admin and no Service Account User on
the project (it may act as the node service account only), but the roles are not tied to the names
of the lab resources, which a role cannot be before the resource exists; the roles were chosen from
the documentation of each service, not by a real apply. The IAM condition limits only project-level
grants. The plan identity can read the
project configuration, its IAM policies and the (non-secret) contract parameter; its subjects accept
only pull requests of this repository and `main`, and fork pull requests never get a token. Use a
**dedicated project** (`scripts/preflight.sh` refuses one that holds a cluster, a database or a
secret of other work) and keep the `lab` environment protected. The project ID and number live in
repository variables; the workflows mask them, but treat the logs as public. The DNS endpoint of the
cluster is reachable from the internet (IAM and RBAC still apply). Core Gateway serves plain HTTP;
full implements Google-managed HTTPS, whose actual issuance remains unrun in the cloud.
Protected DR synchronization has value access only to four exact lab secrets; plan/deploy have none.
See the "Limits" section of docs/GUARDRAILS.md.
